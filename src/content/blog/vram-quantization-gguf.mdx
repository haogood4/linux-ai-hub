# 显存只有 8GB，如何跑起本地大模型：量化、GGUF 与实战指南

你下载了一个 14B 或 32B 模型，页面上写着“推荐 24GB 显存”。再看看自己的显卡：只有 8GB，最多 12GB。模型还没启动，已经被显存要求劝退。

这种情况并不罕见。模型页面标注的显存，通常对应 FP16（16 位浮点数）或更高精度的完整模型。实际部署时，可以通过量化（Quantization）降低模型参数的数值精度，把模型体积压缩到消费级显卡能够承受的范围。

对 8-12GB 显卡来说，量化不是旁门左道，而是运行本地大模型的标准方案。

## 量化是什么：把模型压进有限显存

大语言模型由大量参数组成。每个参数本质上是一个数字，模型运行时需要把这些数字加载到显存或内存中。

以常见的 FP16 为例，每个参数使用 16 位，也就是 2 字节存储。如果一个模型有 7 billion（70 亿）个参数，仅权重就需要约 14GB 空间，实际运行时还要加上运行框架、上下文缓存和临时计算空间。

量化的思路很直接：不用那么多位来表示每个参数。

- FP16：每个参数使用 16 位
- INT8：每个参数使用 8 位
- INT4：每个参数使用 4 位

参数从高精度数字变成低精度整数后，模型权重体积会明显下降。一个原本需要十几 GB 甚至几十 GB 的模型，就可能被压缩到消费级显卡可以处理的范围。

实际量化并不是简单地把所有数字粗暴砍掉。主流方法会把参数分成许多小块，分别记录缩放系数，让不同范围的参数尽量保留原有分布。因此，同样是 4 位量化，不同格式的效果也会有差别。

精度损失主要体现在这些地方：

- 复杂推理可能更容易出错
- 数学计算和代码生成可能略有退化
- 长上下文下的稳定性可能下降
- 小模型在量化后更容易暴露能力不足
- 普通问答、摘要、翻译等任务通常仍然可用

量化不会让模型突然失去语言能力。更准确的说法是：模型仍然保留原来的能力结构，但在边界任务上更容易出现错误。

对于日常聊天、知识问答、写代码和本地知识库检索，4 位或 6 位量化通常已经足够实用。

## GGUF：量化模型的通用格式

GGUF（GPT-Generated Unified Format）是一种面向大语言模型推理的文件格式，最早由 llama.cpp 生态推动，后来成为本地运行量化模型的常见选择。

一个 GGUF 文件通常包含：

- 模型权重
- 模型架构信息
- tokenizer（分词器）配置
- 上下文和特殊 token 配置
- 量化类型等元数据

你会经常看到这样的文件名：

```text
qwen2.5-7b-instruct-q4_k_m.gguf
qwen2.5-7b-instruct-q8_0.gguf
```

其中 `Q4_K_M` 和 `Q8_0` 就是量化档位。

常见关系可以这样理解：

- GGUF 是文件容器和模型格式
- Q4_K_M、Q6_K、Q8_0 是权重的量化方式
- llama.cpp 是负责加载和推理 GGUF 的运行框架
- Ollama 在底层使用 llama.cpp 体系或兼容的推理后端，并将模型管理、对话接口和配置做了封装

因此，看到一个 GGUF 文件时，可以直接想到：它通常能够被 llama.cpp 使用，也可以通过 Ollama 的 `Modelfile` 导入。

## 量化档位怎么选

下面的体积是针对模型权重的约略范围，实际大小会受到模型架构、词表和元数据影响。运行时还要额外占用显存或内存，不能只看文件大小。

| 档位 | 单参数精度 | 权重体积 | 精度表现 | 适用场景 |
|---|---:|---:|---|---|
| `Q8_0` | 8 位 | 约为 FP16 的一半 | 接近高精度模型 | 显存充足，重视代码、推理和稳定性 |
| `Q6_K` | 6 位 | 约为 FP16 的三分之一到一半 | 较好，损失通常不明显 | 想兼顾质量和显存占用 |
| `Q4_K_M` | 4 位 | 约为 FP16 的四分之一到三分之一 | 综合表现好 | 消费级显卡的默认选择 |
| `Q3_K_S` | 3 位 | 体积更小 | 精度损失更明显 | 显存非常紧张，优先保证模型能启动 |

### Q8_0：质量优先

`Q8_0` 通常接近 FP16 的效果，适合代码生成、复杂推理和对输出稳定性要求较高的场景。

缺点是占用空间较大。7B 模型的 Q8 权重通常就需要约 7-8GB，运行时还要加上上下文缓存，所以 8GB 显卡往往无法完整放入显存。

### Q6_K：质量和占用的折中

`Q6_K` 比 Q8_0 更节省空间，质量通常仍然比较接近高精度版本。如果你的显卡有 12GB，或者准备使用部分 CPU 参与推理，Q6_K 是值得优先考虑的档位。

### Q4_K_M：最实用的默认档位

`Q4_K_M` 是本地部署里非常常见的选择。它通常比传统的 4 位格式保留更多重要参数的精度，在体积、速度和输出质量之间取得了不错的平衡。

8GB 显卡运行 7B、8B 模型时，Q4_K_M 通常比较轻松。12GB 显卡运行 14B 模型时，Q4_K_M 也经常是可行起点，但上下文长度、显卡驱动、推理后端和系统内存都会影响最终结果。

### Q3_K_S：最后的空间换时间

`Q3_K_S` 进一步缩小模型体积，适合显存非常有限的机器。但它更容易影响复杂推理、代码和长文本任务。

如果 Q4_K_M 能够运行，通常不建议一开始就降到 Q3_K_S。先降低上下文长度或让部分层交给 CPU，往往比直接使用更低精度更合理。

## 实操一：用 Ollama 零操作运行量化模型（完整部署见 [Ollama 本地部署教程](/tutorials/ollama-local-deploy)）

Ollama 适合不想手动管理模型文件和推理参数的用户。安装 Ollama 前，需要确认：

- 系统已经安装对应显卡驱动
- NVIDIA 用户可以正常使用 `nvidia-smi`
- 硬盘有足够空间保存模型
- 系统内存不能过小，因为显存不足时模型可能使用内存
- 第一次拉取模型需要网络和较大的下载流量

可以先检查 NVIDIA 驱动：

```bash
nvidia-smi
```

然后直接运行一个 7B 模型：

```bash
ollama run qwen2.5:7b
```

Ollama 官方模型通常已经提供适合本地运行的量化版本，常见默认档位接近 4 位量化。也就是说，使用 `ollama run qwen2.5:7b` 时，一般不需要自己下载 FP16 文件再手工压缩。

查看本地模型：

```bash
ollama list
```

查看模型详细信息：

```bash
ollama show qwen2.5:7b
```

如果显存只有 8GB，优先从 7B 或 8B 的默认量化版本开始。显存为 12GB 时，可以尝试更大的 14B 模型：

```bash
ollama run qwen2.5:14b
```

但“能运行”和“全部放进显卡”是两回事。Ollama 可能把部分权重放入显存，剩余部分交给系统内存和 CPU，速度会根据硬件差异明显变化。

### 在 Ollama 中指定 GGUF 档位

如果你从模型仓库下载了具体的 GGUF 文件，可以通过 `Modelfile` 导入。下面以当前目录中的 Q8_0 文件为例：

```text
FROM ./qwen2.5-7b-instruct-q8_0.gguf
PARAMETER num_ctx 4096
```

将这段内容保存为 `Modelfile`，并确保同一目录存在：

```text
qwen2.5-7b-instruct-q8_0.gguf
```

然后执行：

```bash
ollama create qwen25-q8 -f Modelfile
```

运行导入的模型：

```bash
ollama run qwen25-q8
```

如果显存不够，可以把 `FROM` 指向 Q4_K_M 文件：

```text
FROM ./qwen2.5-7b-instruct-q4_k_m.gguf
PARAMETER num_ctx 4096
```

再次创建模型：

```bash
ollama create qwen25-q4 -f Modelfile
ollama run qwen25-q4
```

这里的关键不是模型名称里有没有 `q4`，而是 `FROM` 指向的 GGUF 文件本身使用什么量化档位。文件名只是提示，真正的格式由文件内部元数据决定。

## 实操二：用 llama.cpp 精确控制显存

llama.cpp 更适合希望自己控制模型文件、上下文长度和 GPU offload（GPU 层卸载）比例的用户。

使用前需要准备：

- 已经编译好或安装好的 llama.cpp
- 一个可用的 GGUF 模型文件
- 对应的 GPU 后端，例如 CUDA、Metal 或 Vulkan
- 能够正常工作的显卡驱动

下面假设 llama.cpp 的命令行程序叫 `llama-cli`，模型文件位于当前目录的 `models` 文件夹。

让程序尽可能把模型层放入显卡：

```bash
./llama-cli -m ./models/qwen2.5-7b-instruct-q4_k_m.gguf -ngl 99 -c 4096 -p "请用三句话解释什么是量化模型"
```

参数含义如下：

- `-m`：指定 GGUF 模型文件
- `-ngl 99`：尝试卸载尽可能多的模型层到 GPU
- `-c 4096`：设置上下文长度
- `-p`：设置提示词

如果 8GB 显卡无法容纳全部层，可以降低 `-ngl`，例如：

```bash
./llama-cli -m ./models/qwen2.5-14b-instruct-q4_k_m.gguf -ngl 20 -c 2048 -p "写一段介绍 Linux 量化推理的短文"
```

`-ngl 20` 表示只把部分层放入 GPU，剩余工作由 CPU 和系统内存承担。具体应该设置多少，需要根据显卡显存、模型大小、上下文长度和后端实现逐步尝试。

可以先使用较低的上下文长度：

```bash
./llama-cli -m ./models/qwen2.5-14b-instruct-q4_k_m.gguf -ngl 20 -c 1024 -p "列出三个使用本地大模型的场景"
```

上下文越长，KV cache（键值缓存）通常越大。模型权重勉强放入显存时，把上下文从 8192 降到 4096 或 2048，可能比继续降低量化档位更有效。

## 常见误区与边界

### 量化不等于模型“变蠢”

量化会带来精度损失，但损失程度取决于模型规模、量化方法和任务类型。一个较大模型使用 Q4_K_M，实际效果可能仍然优于一个更小的高精度模型。

真正需要关注的是任务：

- 日常问答：Q4_K_M 通常够用
- 代码生成：Q6_K 或 Q8_0 更稳妥
- 数学推理：优先选择更大模型和更高档位
- 轻量聊天：Q3_K_S 也可能可以接受

### 显存不是唯一瓶颈

显存只决定 GPU 能放下多少内容。完整运行还会受到以下资源限制：

- 系统内存：CPU 兜底时需要容纳未卸载的模型部分
- 硬盘：模型文件可能从几 GB 到几十 GB
- 内存带宽：CPU 参与越多，速度通常越容易下降
- 上下文缓存：长对话会增加额外内存占用
- 显卡驱动和推理后端：决定 GPU 是否真正参与计算

因此，显存不足时不要只盯着显卡。一个拥有 32GB 系统内存的 8GB 显卡机器，通常比只有 16GB 系统内存的同款显卡更容易运行大模型。

### 量化救不了模型规模不匹配

量化只能降低每个参数的存储成本，不能改变模型本身的参数数量和能力上限。

一个 3B 模型即使使用 Q8_0，也不会因为精度更高就自动拥有 14B 模型的复杂推理能力。反过来，70B 模型即使使用 Q3_K_S，仍然可能需要大量系统内存，CPU 推理速度也可能难以接受。

选择顺序应该是：

1. 先确定模型规模是否适合任务
2. 再选择能接受的量化档位
3. 最后调整 GPU 层数和上下文长度

## 小结：先从 Q4_K_M 开始

对 8-12GB 消费级显卡，本地大模型可以按照下面的思路选择：

- 7B 或 8B：优先使用 Q4_K_M
- 14B：12GB 显卡可以先试 Q4_K_M，8GB 显卡准备 CPU 兜底
- 代码和复杂推理：显存允许时升级到 Q6_K 或 Q8_0
- 显存特别紧张：再考虑 Q3_K_S
- Ollama：默认模型通常已经完成量化，先直接 `ollama run`
- llama.cpp：用 `-ngl` 控制放入 GPU 的层数（见[llama.cpp 推理教程](/tutorials/llama-cpp-inference)）
- 启动失败或速度过慢：先减少上下文、降低 GPU 层数，并检查系统内存

可以记住这句口诀：

> **默认先选 Q4_K_M，Ollama 通常已量化；显存不够降 `-ngl`，内存硬盘也要留余量；想要更稳上 Q6，极限省空间才用 Q3。**

量化的价值，不是把一张小显卡伪装成高端显卡，而是让模型规模、精度和硬件资源之间有一个可操作的平衡点。只要接受部分 CPU 参与，并合理控制上下文长度，8GB 显卡也能进入本地大模型的实用范围。
