# 本地 AI 工具链全景图：先跑起来，再逐层升级

听起来像折腾，其实已经成熟。今天的本地 AI 不再只是“下载一个模型、打开命令行”这么简单：对话、图片、视频、语音、知识库和自动化，已经形成了相对清晰的工具链。

真正容易踩坑的地方，是把所有名词误认为“必须安装的软件”。Ollama、Open WebUI、Stable Diffusion、RAG、MCP 分属不同层级，解决的问题也不同。理解这张地图之后，你可以从最简单的本地对话开始，按需求增加能力，不必一次性搭完整套系统。

## 第一层：模型运行时，一切的地基

模型运行时（Runtime）负责加载模型、分配显存或内存，并提供生成文本的接口。它相当于本地 AI 的发动机，聊天界面、知识库和自动化工具最终都要通过它调用模型。

### Ollama：最适合入门

Ollama 把模型下载、运行和服务接口整合到了一起，适合第一次搭建本地大语言模型环境的用户。它默认提供本地 API，常用模型可以直接通过一条命令运行。

Linux 或 macOS 上，可以使用官方安装脚本：

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

这条命令会从官方地址下载并执行安装脚本。脚本会根据系统架构选择版本，并在 Linux 上安装到系统目录；macOS 上则安装 Ollama 应用。执行前要确认网络环境和下载来源可信，也要注意命令可能请求管理员权限。Windows 用户可以使用对应的官方桌面安装方式，不应直接套用这条 Unix 命令。

安装完成后运行一个模型：

```bash
ollama run qwen3
```

首次运行通常会下载模型文件，耗时和占用空间取决于模型大小。启动后，你可以直接在终端对话，也可以让其他应用通过本地 API 调用它。

**什么时候需要 Ollama：** 想在个人电脑上聊天、总结、写代码，或者希望快速验证某个模型是否适合自己时，先装 Ollama 就够了。详细步骤可参考 [Ollama 本地部署](/tutorials/ollama-local-deploy)。

### llama.cpp：需要更细控制时

llama.cpp 是面向单机推理的开源项目，常用于运行量化模型。它提供更细的参数控制，适合研究模型格式、量化等级、CPU/GPU 分层加载和嵌入式部署。

它并不是 Ollama 的“必装替代品”。很多底层能力与 llama.cpp 生态有关，但入门阶段没有必要绕过 Ollama 直接配置编译环境。

**什么时候需要 llama.cpp：** 你需要运行特殊格式模型、研究量化参数、在资源有限的设备上精细调优，或者希望把推理能力嵌入自己的程序时，再看 [llama.cpp 推理](/tutorials/llama-cpp-inference)。

### vLLM：面向服务化和并发

vLLM 更偏向服务器部署。它擅长把模型作为高吞吐 API 服务提供给多个用户或多个应用，适合团队内部服务、批量任务和生产环境。

它通常需要更明确的 GPU、CUDA、模型格式和服务参数配置。个人电脑只想和模型聊天时，使用 vLLM 往往增加了部署复杂度。

**什么时候需要 vLLM：** 当你已经确认模型和业务需求，需要同时服务多个请求，或者要搭建稳定的内部推理服务时，再参考 [vLLM 服务化部署](/tutorials/vllm-serving)。

选择顺序可以很简单：先 Ollama，遇到单机优化问题再看 llama.cpp，有并发服务需求再考虑 vLLM。

## 第二层：对话界面，给模型配个“壳”

命令行适合测试，但长期使用通常需要浏览器界面。Open WebUI 是常见的本地聊天前端，可以连接 Ollama，提供会话管理、文件上传、多模型切换和知识库等功能。

它的价值不在于“让模型变聪明”，而是把模型运行时包装成更适合日常使用的工作台。你可以把不同模型用于代码、写作和翻译，也可以在聊天中上传文档，让系统结合文件内容回答问题。

Open WebUI 通常通过 Docker 部署。使用 Docker 前，需要确认 Docker Desktop 或 Docker Engine 已正常运行；如果要让容器直接使用 NVIDIA GPU，还要额外配置显卡驱动、CUDA 运行时和 NVIDIA Container Toolkit。不要把“宿主机能识别显卡”直接等同于“容器已经能用显卡”。

**什么时候需要 Open WebUI：** 你不想每次通过命令行操作，或者需要多人共享、文件问答、历史会话和多模型管理时，再安装它。可以参考 [Open WebUI 部署](/tutorials/open-webui)。

## 第三层：生图与视频，创作类模型

文本模型和图像模型是两套不同的工具链。Ollama 不能直接替代 Stable Diffusion，也不能自动变成视频生成平台。

### Stable Diffusion WebUI：成熟的图像工作台

Stable Diffusion WebUI 提供模型选择、提示词、采样参数、图片尺寸和插件管理等功能。它的优势是资料多、教程多、扩展丰富，适合想快速生成图片并逐步学习参数的人。

**什么时候需要它：** 你需要文生图、图生图、局部重绘、放大或常见插件功能，而且希望使用相对传统的界面时，选择 [Stable Diffusion WebUI](/tutorials/stable-diffusion)。

### ComfyUI：节点化工作流

ComfyUI 把生成过程拆成节点。模型加载、提示词编码、采样、控制图和放大都可以明确连接，适合搭建可复用、可批量执行的工作流。

它的学习曲线比传统 WebUI 更陡，但当流程变复杂时，节点结构更容易保存和复现。

**什么时候需要它：** 你要组合多个模型、固定复杂流程、批量生成，或者希望精确理解每一步处理过程时，再学习 [ComfyUI 基础工作流](/tutorials/comfyui-basic-workflow)。

视频模型如 Wan、LTX 等可以在消费级显卡环境中尝试，但是否能顺畅运行取决于显存、模型版本、分辨率、帧数和工作流配置。不要只看模型名称判断硬件是否足够，先从较小参数和短视频任务开始。入门路径可参考 [AI 视频生成](/tutorials/ai-video-generation)。

## 第四层：语音，听懂你、说给你

语音系统通常分为两个方向：

- 语音合成（TTS, Text-to-Speech）：把文字转换成语音。
- 语音识别（ASR, Automatic Speech Recognition）：把语音转换成文字。

Whisper 是常见的 ASR 方案，适合把会议录音、语音输入和视频字幕转换为文字。CosyVoice 属于 TTS 方向，能够生成自然语音，并支持一定程度的声音克隆能力。声音克隆涉及授权和隐私，使用他人声音前必须获得明确许可。

**什么时候需要语音工具：** 只有在你要做语音助手、字幕、播客、有声内容或语音交互时才安装。文字对话阶段可以完全跳过。相关内容可查看 [本地 TTS](/tutorials/local-tts)。

## 第五层：知识库与自动化，让 AI 用上你的资料

大语言模型本身并不会自动掌握你的硬盘文件、公司制度或项目文档。知识库系统通常采用知识库检索增强生成（RAG, Retrieval-Augmented Generation）：

1. 把文档切成较小片段。
2. 将片段转换为向量。
3. 用户提问时检索相关片段。
4. 把检索结果和问题一起交给模型生成回答。

RAG 适合规章制度、产品手册、代码文档和个人资料查询，但它不是训练模型。文档切分、向量模型、召回数量和权限控制都会影响结果。

**什么时候需要 RAG：** 当你开始频繁询问自己的资料，并且希望回答能引用文档内容时，再搭建 [RAG 知识库](/tutorials/rag-knowledge-base)。单纯聊天或写作不需要先装知识库。

Dify 是面向应用搭建的可视化平台，可以把模型、提示词、知识库、条件判断和外部接口连接成工作流。它比手写后端更适合验证业务流程，但部署组件较多，包含数据库、缓存或文件存储等依赖时，需要认真规划数据目录和备份。

**什么时候需要 Dify：** 你要做一个可供他人使用的问答应用、客服流程、文档处理流程，而不是只在个人聊天窗口里使用模型时，可以参考 [Dify 可视化 AI 平台](/tutorials/dify-visual-ai-platform)。

Function Calling 让模型输出结构化的工具调用请求，例如查询天气、读取数据库或创建工单。模型上下文协议（MCP, Model Context Protocol）则提供了更统一的模型与外部工具连接方式。

这类能力会扩大系统权限范围。接入文件、命令行、数据库或网络服务时，应采用最小权限、明确的参数校验和人工确认机制。

**什么时候需要 Function Calling 或 MCP：** 当模型需要执行动作，而不只是生成文字时再使用。可以从 [Function Calling 与 MCP](/tutorials/function-calling-mcp) 开始。

## 第六层：硬件与容器，底座问题

本地 AI 的核心硬件指标通常是显存容量。模型参数量、量化等级、上下文长度和并发数量都会影响显存需求。显存不足时，部分运行时可以把计算放到系统内存或 CPU，但速度和可用配置会发生变化。

选购或评估设备时，要同时看 GPU 显存、系统内存、磁盘空间、驱动版本和散热条件。模型文件可能占用大量磁盘，视频和图像工作流还会产生缓存与中间文件。可先根据任务类型查看 [硬件参考](/hardware)。

Docker 适合隔离多个服务，例如 Ollama、Open WebUI、向量数据库和 Dify。它能减少依赖冲突，也方便迁移，但不会自动解决显卡驱动问题。GPU 容器需要宿主机驱动、容器运行时和框架版本彼此兼容，升级前应保留配置和数据备份。具体可参考 [Docker GPU 容器](/tutorials/docker-gpu-containers)。

不熟悉 Linux 的用户也可以先在现有系统中使用原生应用或 Docker Desktop，逐步验证需求后再考虑更复杂的服务器部署。[Linux 试用指南](/blog/try-linux-without-risk)适合希望低风险了解 Linux 的读者。

## 一条渐进路径：先能用，再进阶

### 第一步：本地对话

先安装 Ollama，运行：

```bash
ollama run qwen3
```

确认模型能正常下载、启动和回答问题。此时不要急着安装知识库、向量数据库或自动化平台。

### 第二步：浏览器使用

当你需要会话历史、文件上传、多模型切换时，再加入 Open WebUI。先把它当作 Ollama 的前端，不要一开始就配置复杂插件。

### 第三步：尝试生图

有明确的图片需求后，选择 Stable Diffusion WebUI。需要节点工作流、批处理或更细控制时，再转向 ComfyUI。视频生成放在图像之后，先确认显存和存储空间。

### 第四步：接入个人资料

当你拥有稳定的文档问答需求，再部署 RAG。资料规模和权限较复杂时，可以用 Dify 组织应用流程。

### 第五步：加入语音与工具调用

最后再接入 Whisper、CosyVoice、Function Calling 或 MCP。此时系统已经有明确用途，权限边界、日志和错误处理也更容易设计。

本地 AI 工具链是地图，不是清单：先装 Ollama，再按需求添加界面、生图、知识库、语音和 MCP，能用一层就验证一层。
